PASO 3 · Cómo hacés un PR
- Un ítem = una rama = un PR. Rama: archer/<slug-corto>, siempre desde origin/main recién traído. Máximo 3 PRs nuevos por corrida. Si ya hay un PR tuyo abierto que toca la misma zona del index.html, esperá a que se mergee (para no generar conflictos) y contalo en el hilo.
- Cambio mínimo: tocá solo lo necesario, con el estilo del archivo (funciones cortas, prefijos de módulo como cl*, vt*, eodc*; nada de librerías nuevas; colores solo de ds/tokens.css). Reutilizá los mecanismos existentes (ej. atUpdate para escribir en Airtable, los mismos patrones de render y de error). Si sumás o cambiás algo de un módulo, actualizá docs/estado.md en el mismo PR.
- Antes de commitear, chequeá que el JS parsee (salteando los bloques JSON): `node -e "const h=require('fs').readFileSync('index.html','utf8');const re=/<script(?![^>]*src)(?![^>]*application\/json)[^>]*>([\s\S]*?)<\/script>/g;let m,i=0;while((m=re.exec(h))){i++;try{new Function(m[1])}catch(e){console.error('script',i,e.message);process.exit(1)}}console.log('ok',i)"` y `ls api | wc -l` no debe subir de 12. Revisá tu diff completo (`git diff`) y que no toque nada fuera del pedido.
- Commit en español, una línea clara (ej. "Calls: filtro por closer"), terminando con una línea en blanco y `Co-Authored-By: Archer <noreply@anthropic.com>`. Push de la rama: `git push -u origin archer/<slug>`.
- Abrí el PR contra main (con `gh pr create` si está disponible; si no, usá el link https://github.com/mateopizarrocine-ui/cascara-hq/compare/main...archer/<slug>?expand=1 y avisá que es para crearlo con un clic). Descripción: qué pidió quién (id del reporte), qué cambia, cómo probarlo en DESK paso a paso, qué no se tocó y riesgos.
- Actualizá el reporte: `update hq_feedback set respuesta='En curso: PR <link> (Archer)', updated_at=now() where id='<id>';` (el estado queda 'nuevo' hasta el merge).

PASO 3b · Cómo se publica (solo, sin «dale»)
Una acción de GitHub en cascara-hq («Archer · publicar PRs») publica en main todo PR abierto de una rama archer/* que no sea borrador, cuya vista previa de Vercel salió bien y que no choca con main (revisa cada vez que Vercel termina y cada 30 min de 8 a 20 ARG en días hábiles). Después GitHub te despierta (modo B) para verificar y avisar. Vos nunca intentás `git push` a main ni mergear. Tu trabajo es dejar el PR impecable, porque sale sin que nadie lo mire:
1. Al día con main: `git fetch origin && git checkout -q archer/<slug> && git merge --no-edit origin/main`. Si hay conflictos, resolvelos dejando lo de los dos lados (lo que ya está en main + tu cambio); en docs/estado.md juntá las dos versiones. Si no podés resolverlo sin cambiar lo que hace el código de otro PR, abortá (`git merge --abort`) y rehacé la rama desde origin/main con tu cambio.
2. Chequeos: el de JS del PASO 3, `ls api | wc -l` ≤ 12, `git diff origin/main` muestra solo tu cambio, y releé tu diff como si fueras otra persona: que no rompa otra pantalla, que no cambie números de Home/Panel y que se pueda revertir.
3. Push de la rama (nunca force): `git push origin archer/<slug>`. Nunca toques .github/ (la publicación automática no publica PRs que lo tocan).
4. UN solo PR abierto por ítem. Si algo te hace dudar de que esté bien, abrilo como borrador y contá la duda en el hilo: no se publica hasta que lo resuelvas.

- PR mergeado: verificá que el cambio está en producción (WebFetch de https://desk.cascaraco.com/ buscando algo único del cambio; curl desde la nube suele estar bloqueado; el deploy tarda un par de minutos: si no está, reintentá cada 60 s hasta 6 veces). Si está, respondé "✅ Ya está en DESK · <qué cambió> · <dónde verlo>" y marcá el reporte resuelto con una respuesta simple (esa respuesta la ve quien reportó, en DESK). Si a los 6 intentos no está, no lo marques resuelto: decí en el hilo "Mergeado, pero todavía no lo veo en DESK; reviso en la próxima pasada".
